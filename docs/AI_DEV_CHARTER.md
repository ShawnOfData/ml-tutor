# ML-Tutor AI 开发宪法

> 本文档是 **ml-tutor** 项目的第一份、也是最上位的开发约束文档。
> 任何 AI 助手、开发者在本仓库内工作前，必须**完整阅读并承诺遵守**。
> 违反宪法的产物一律视为无效。

---

## 第 1 条 · 严禁编造接口（最高优先级）

### 1.1 不可编造的内容
- 不得凭空臆测或"猜测"任何函数签名、类属性、模块路径、API 端点、配置字段、参数名、返回值结构。
- 不得编造依赖库的存在、版本、API 调用方式。
- 不得编造数据库表结构、Schema、索引名、外键关系。
- 不得编造环境变量、配置文件字段、CLI 参数名。
- 不得编造 HTTP 状态码、请求/响应结构、WebSocket/SSE 事件类型。

### 1.2 强制工作流程（先做什么再做什么）
1. **所有改动必须先阅读现有代码**：用 Read / Search / Grep 定位真实实现，确认文件路径、函数签名、参数类型、调用约定。
2. 不确定时，**用搜索/阅读验证**，不得靠记忆或"看起来像是"推断。
3. 无法确认时，**停止修改，向用户提问**（例如"我在 XX 文件里没找到 YY，你确认一下？"）。
4. 如果发现接口与自己预期不符，**以代码为准**，不要假设"应该是这样"。

### 1.3 判定标准
- 提交代码中出现"我猜这里应该有个 XXX"或类似注释 → 违规，立即修正。
- 出现未验证的 import、调用、参数 → 违规。
- 出现"先这样写，后面再改"的占位实现 → 违规（可在报告里记录 TODO，但不能让它出现在主分支）。

## 第 2 条 · 文件命名、位置与注释规范

### 2.1 文件命名
- **Python**：全小写 + 下划线（`retrieval_cache.py`、`query_normalizer.py`），类名大驼峰。
- **TypeScript / TSX**：组件文件大驼峰（`ChatSidebar.tsx`），工具/ hooks 全小写（`useRagSearch.ts`）。
- **配置 / YAML**：全小写 + 下划线（`embedding_config.yaml`）。
- **目录**：全小写 + 下划线（`rag/`、`knowledge_bases/`、`services/`）。
- **报告**：见第 4 节模板。

### 2.2 文件位置
- 遵循项目现有分层：`services/`（领域服务）→ `pipelines/`（流水线）→ `api/routers/`（HTTP 入口）。
- 新增模块优先**并入现有目录结构**，不创建新的顶层目录除非用户批准。
- 新文件创建前，先确认它是不是应该存在——如果现有文件里已有类似功能，**优先在现有文件追加**，不要拆出新文件。

### 2.3 注释规范（简明 = 好注释）
- 每个文件顶部写**一行模块说明**（它是干什么的）。
- 每个 public 类 / 函数写**一句话 docstring**，说明它的职责与关键参数。
- **不要写"代码翻译式注释"**——如果代码本身可读，注释是冗余。
- 写"为什么"而非"是什么"：注释解释复杂逻辑、设计取舍、坑点，不解释显而易见的 `for i in range(n)`。
- 改代码时，**同步更新/删除过时注释**（注释和代码不一致比没注释更糟）。

### 2.4 禁止事项
- 不用废弃代码（`# 旧版本代码`、`TODO 等会重写`）——要用 git 历史追溯。
- 不用"占位代码"（`raise NotImplementedError`、`pass` 的桩实现）——除非在测试中。
- 不用注释块替代文档，不用注释解释 git 历史。

## 第 3 条 · 问题与环境必须报备

### 3.1 什么必须报备
- **开发受阻**：代码理解不了、依赖冲突、接口不明确、逻辑不确定。
- **设备环境问题**：Ollama 没装、向量索引不可用、Python/Node 版本不匹配、端口被占、磁盘/内存不足。
- **外部资源依赖**：需要联网下载模型、需要付费 API、需要数据库服务。
- **安全 / 合规**：发现密钥泄漏、数据隐私问题、第三方库许可证问题。

### 3.2 报备格式
向用户报告问题时，必须包含：
1. **问题是什么**（一句话）；
2. **影响范围**（卡在哪个阶段、哪个模块）；
3. **已尝试了什么 / 为什么解决不了**；
4. **建议方案**（2~3 个选项，标明推荐）。

### 3.3 禁止事项
- 不报就跳过——"先写了再说，有问题再说" → 违规。
- 隐瞒问题——"这个 warning 先不管" → 违规，必须记录在报告里。
- 自行替换依赖或升级/降级版本而不告知用户。

## 第 4 条 · 分阶段 / 分模块开发 + 报告机制

### 4.1 阶段划分（当前规划，可随项目推进迭代）

| 阶段 | 内容 | 交付物 |
| --- | --- | --- |
| **Phase 0** | 项目骨架建立：目录结构、AI 开发宪法、基础 README、.gitignore、依赖确认 | 宪法、目录、报告 P0 |
| **Phase 1** | RAG 提速：进程内索引缓存、检索结果缓存、去掉全量校验、Ollama 预热 | 代码 + 报告 P1 |
| **Phase 2** | 检索质量：结构感知切块（ML 教材适配）、混合检索调优、来源引用增强 | 代码 + 报告 P2 |
| **Phase 3** | 个性化教学方案：学员画像、学习路径生成、测评反馈闭环 | 代码 + 报告 P3 |
| **Phase 4** | 前端瘦身与体验：裁剪无关模块、流式问答优化、SSE 在单向流场景落地 | 代码 + 报告 P4 |

> **规则**：阶段不可跳过，但可微调顺序或合并相邻小模块。任何阶段开始前，先出一份**阶段启动说明**（存在 `reports/` 里），列明模块清单与依赖关系。

### 4.2 报告格式

每完成一个**模块**（不是整个阶段），写一份报告到 `reports/` 目录。阶段内的每个模块各自一份，阶段结束再合一份阶段总结。

#### 文件命名
```
reports/
├── P0_skeleton_report.md
├── P1_RAG_speed_index_cache_report.md
├── P1_RAG_speed_result_cache_report.md
├── P1_RAG_speed_final_report.md
├── P2_chunker_report.md
└── ...
```
格式：`P{phase}_{module}_report.md`。

#### 报告必备 6 项
```markdown
# P{phase} {模块名} 模块报告

**完成时间**：YYYY-MM-DD
**负责人**：[你自己]
**状态**：✅ 完成 / ⚠️ 部分完成（写明缺口）

## 1. 开发内容（做了什么）
- 要点 A
- 要点 B
- （尽量具体，"做了什么"比"改了哪几行"更有用）

## 2. 涉及文件
| 文件路径 | 改动类型（新增/修改/删除） | 作用 |
| --- | --- | --- |
| ml_tutor/services/rag/xxx.py | 修改 | 做了 XXX |

## 3. 需要警惕的问题（坑 / 风险 / 未解决事项）
- 问题 A：[描述]，后续建议 [TODO 或说明为什么暂时不解决]
- 问题 B：[描述]

## 4. 需要对接的内容（下游依赖谁 / 谁依赖我）
- 本模块依赖：[模块 / 文件 / 外部服务]
- 依赖本模块的：[模块 / 文件]
- 接口变更：[如果有，列出旧 → 新]

## 5. 测试与验证（怎么证明"能用"）
- 单元测试：[是否有 / 命令 / 结果]
- 手动验证：[做了什么、看到什么]
- 性能：[如果是提速项，给出 before / after 数字]

## 6. 后续建议
- 下一步建议做什么 / 如何继续推进
- 与其他阶段的协作点
```

---

## 第 5 条 · 质量底线

- **代码可运行** + 报告可查证，两者都要有才算完成。
- 每阶段结束前做一次**自审**：对照宪法检查 1~4 条。
- 发现违反宪法的产物，**立即修正**，不得带病进入下一阶段。

---

## 附 · 宪法变更机制

宪法本身可以迭代，但变更需：
1. 在 `docs/AI_DEV_CHARTER.md` 里改；
2. 写明变更日期、原因、变更内容；
3. 保留历史版本（git 追溯即可）。
